# Структура дипломной работы

Документ помогает синхронизировать текст диплома с реальной реализацией, без «академической истории», оторванной от кода.

## Рекомендуемое название

**«Интеллектуальная система мониторинга безопасности IoT»**

Подзаголовок (опционально):

**«Проектирование и реализация локального прототипа для детекта угроз по телеметрии»**

## Рекомендуемая структура глав

1. **Введение**
2. **Постановка задачи**
3. **Объект и предмет исследования**
4. **Цель и задачи**
5. **Обзор технологий и подходов**
6. **Требования к системе**
7. **Проектирование архитектуры**
8. **Модель угроз и логика детекта**
9. **Реализация**
10. **Тестирование и эксперименты**
11. **Результаты и практическая значимость**
12. **Ограничения**
13. **Заключение**
14. **Перспективы развития**

## Краткое содержание по главам

### 1) Введение

- актуальность IoT-безопасности;
- почему важен мониторинг;
- почему выбран локальный прототип.

### 2) Постановка задачи

- проблема обнаружения аномалий в разнородной telemetry;
- необходимость простого, объяснимого решения.

### 3) Объект и предмет

- объект: процессы мониторинга IoT в контролируемой среде;
- предмет: методы и ПО для сбора telemetry, детекта угроз и визуализации.

### 4) Цель и задачи

Цель: реализовать локальный прототип, который собирает telemetry, выявляет подозрительное поведение и визуализирует алерты.

Задачи должны прямо отражать roadmap и фактический код.

### 5) Обзор

- rule-based vs anomaly-based подход;
- обоснование выбора FastAPI/MQTT/SQLite/Jinja2/Chart.js;
- акцент: не enterprise SIEM, а дипломный прототип.

### 6) Требования

Функциональные:

- 4+ типа устройств;
- MQTT ingest;
- хранение состояния и алертов;
- 5+ сценариев угроз;
- API и dashboard.

Нефункциональные:

- локальный запуск;
- воспроизводимость;
- объяснимость;
- простота сопровождения.

### 7) Архитектура

Опирается на `docs/architecture.md`:

- диаграмма;
- компоненты;
- потоки данных;
- модель данных;
- rationale решений.

### 8) Модель угроз

Опирается на `docs/threat-model.md`:

- активы;
- сценарии;
- границы доверия;
- правила и risk scoring.

### 9) Реализация

- backend модули;
- simulator;
- БД;
- UI;
- сценарный контроль.

Важно: описывать только реально реализованное.

### 10) Тесты и эксперименты

Опирается на `docs/testing.md`:

- unit/integration/API;
- сравнение normal vs attack;
- скриншоты и API evidence.

### 11) Результаты и ценность

- что реально работает;
- какие угрозы детектируются;
- как UI помогает интерпретировать риск.

### 12) Ограничения

- локальный прототип, не production;
- симуляция вместо большого реального парка устройств;
- rules-first ограничивает глубину детекта неизвестных атак.

### 13) Заключение

- достигнутая цель;
- ключевые технические результаты;
- практическая значимость.

### 14) Перспективы

Только реалистичные post-MVP пункты:

- optional anomaly layer;
- PostgreSQL;
- экспорт отчетов;
- один реальный IoT девайс.

## Чеклист доказательств для текста

- архитектурная схема;
- скриншоты основных страниц;
- таблица типов устройств;
- таблица сценариев угроз;
- примеры алертов;
- результаты тестов;
- финальный список реализованных MVP-фич.

## Критерий готовности дипломного текста

- главы соответствуют реальной реализации;
- нет необоснованных заявлений про «сильный AI» и production-grade уровень;
- выводы подкреплены воспроизводимыми доказательствами.
