# Командный workflow

Документ определяет, как студентам и coding-agents работать вместе, чтобы проект стабильно двигался к MVP.

## Цели

- согласованная работа без хаоса;
- контроль scope;
- синхронность кода и документации;
- понятная передача задач между участниками.

## Базовые правила

- `Todo.md` — главный бриф.
- Границы MVP фиксированы, пока руководитель не изменит их явно.
- Сначала rules-only, потом optional ML.
- Любое архитектурное изменение отражается в docs.
- Не добавлять enterprise-сложность в дипломный прототип.

## Роли

- **Backend owner**: FastAPI, DB, MQTT ingest, rules, alerts.
- **Simulation owner**: профили устройств, сценарии, seed.
- **UI owner**: Jinja2/Chart.js и UX-поток страниц.
- **Docs/QA owner**: README/docs, тесты, demo-script, артефакты защиты.

В маленькой команде роли можно объединять, но ответственность должна быть явной.

## Ветки и задачи

### Branching

- `main` — всегда runnable или близко к runnable;
- feature-ветка — одна понятная задача.

Примеры имен:

- `feature/mqtt-ingest`
- `feature/rule-engine`
- `feature/dashboard-overview`
- `docs/diploma-pack`

### Slicing задач

Хорошие задачи:

- добавить `GET /health`;
- добавить модель `Device`;
- реализовать flood rule;
- сделать страницу alerts.

Плохие задачи:

- «сделать весь backend»;
- «доделать весь UI»;
- «закрыть все security фичи».

## Definition of Ready

Задача готова к работе, если:

- цель ясна;
- область изменений понятна;
- есть проверяемый критерий результата;
- задача вписывается в MVP scope.

## Definition of Done (для любой задачи)

Задача закрыта, если:

- реализация завершена;
- docs обновлены (если поведение изменилось);
- есть локальная верификация;
- любой участник может коротко объяснить результат.

## Checklist к review/PR

- изменение в рамках MVP?
- соответствует архитектуре?
- код читаем студентами?
- reason в алертах человеко-понятный?
- docs обновлены при необходимости?
- есть тесты или явная manual-проверка?

## Правила обновления документации

Обновлять docs сразу при изменении:

- startup path;
- repo structure;
- MQTT topics;
- device payload schema;
- alert types/risk scoring;
- demo flow.

## Правила для coding-agent

- читать `Todo.md` до архитектурных решений;
- следовать фазам из `docs/roadmap.md`;
- не добавлять неописанные фичи;
- держаться стека FastAPI/MQTT/SQLite/Jinja2/Chart.js;
- считать ML опциональным;
- синхронизировать код и docs.

## Шаблон handoff

Передавая работу, указывать:

- что сделано;
- что работает сейчас;
- что заблокировано;
- какие файлы изменены;
- как проверить;
- какая следующая smallest task.

## Ритм синхронизаций

- начало недели: короткий план;
- середина: интеграционный sync;
- конец: demo-ready checkpoint.

Каждый sync отвечает на вопросы:

- что работает;
- что сломалось;
- что обновили в docs;
- какой следующий минимальный шаг.

## Критерий готовности workflow

- роли ясны;
- задачи нарезаны на reviewable куски;
- docs не расходятся с кодом;
- handoff-и понятны;
- команда движется к MVP, а не в сторону лишних фич.
