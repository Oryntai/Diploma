# Модель угроз

Документ определяет, что именно мы защищаем в MVP, какие угрозы демонстрируем и как их детектируем без выхода за дипломный scope.

## Цель

Цель не в защите реального промышленного флота IoT.

Цель в том, чтобы прототип:

- распознавал подозрительное поведение;
- создавал понятные алерты;
- позволял аргументированно обсуждать риск на защите.

## Границы

В scope:

- симулированная telemetry;
- локальный MQTT-поток;
- backend validation + rule evaluation;
- генерация алертов и отображение в UI.

Вне scope MVP:

- enterprise PKI/IAM;
- zero-trust архитектура;
- интернет-масштаб и промышленная отказоустойчивость;
- полная forensics в реальных сетях.

## Защищаемые активы

1. Целостность идентичности устройства (`device_id`).
2. Достоверность telemetry.
3. Операционное состояние устройств.
4. Понятность и защищаемость алертов.
5. Воспроизводимость демо.

## Акторы

- легитимный оператор;
- легитимное симулированное устройство;
- подозрительное/компрометированное устройство;
- spoofed identity sender.

## Границы доверия

1. Simulator -> MQTT broker
2. MQTT broker -> Backend ingest
3. Backend processing -> DB
4. Backend -> Dashboard

На каждой границе возможны невалидные данные, перегрузка или потеря объяснимости.

## Приоритетные сценарии

### 1) Message Flood

- устройство публикует слишком часто;
- детект по количеству сообщений в окне времени.

### 2) Impossible Values

- значения вне допустимых диапазонов;
- детект по профилю устройства и валидным интервалам.

### 3) Unknown/Spoofed Identity

- unknown `device_id` или mismatch topic/payload identity;
- unknown sender логируется и алертится, но не становится trusted.

### 4) Repeated Auth Failures

- серия неудачных аутентификаций (например, smart lock).

### 5) Firmware Mismatch/Outdated

- версия вне допустимого списка.

### 6) Frequent Reboot/Unstable State

- слишком частые state transitions.

### 7) Behavior Deviation

- отклонение от baseline (эвристики в MVP, optional ML позже).

## Severity и риск-оценка

- `low`: необычно, но не критично
- `medium`: подозрительно, нужна проверка
- `high`: сильный сигнал компрометации/спуфинга

Рекомендуемое начисление:

- low +15
- medium +30
- high +50
- максимум 100

## Маппинг угроз на меры

- невалидный payload -> schema validation + safe reject;
- flood -> пороги частоты + flood rule;
- spoofing -> registry + topic/payload check;
- firmware risk -> allowlist/поддерживаемые версии;
- скрытое поведение -> metrics + context на device detail.

## Критерий готовности threat-model части

- детектируется минимум 5 сценариев;
- у каждого есть тип/severity/reason/risk;
- результаты видны в API/UI;
- команда четко объясняет, что в scope и что вне scope;
- ML подается как enhancement, а не обязательное ядро.
